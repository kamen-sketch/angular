F-01  Loop proteksi mXSS berhenti prematur, tidak pernah mencapai fixed point
      BERKAS  : packages/core/src/sanitization/html_sanitizer.ts:314-326
      SIFAT   : cacat logika (off-by-one pada pipelining)
      DAMPAK  : garda fail-closed menjadi fail-open (kode mati); regresi
                defense-in-depth. BUKAN XSS — dibuktikan di Chromium 141 nyata.
      BUKTI   : analysis/evidence/mxss-loop-real-chromium.png
                analysis/tools/mxss-browser/ (reproduksi Playwright)
==============================================================================

  KODE APA ADANYA
  ---------------
      let mXSSAttempts = 5;
      let parsedHtml = unsafeHtml;

      do {
        if (mXSSAttempts === 0) {
          throw new Error('Failed to sanitize html because the input is unstable');
        }
        mXSSAttempts--;

        unsafeHtml = parsedHtml;
        parsedHtml = inertBodyElement!.innerHTML;              // (A)
        inertBodyElement = inertBodyHelper.getInertBodyElement(unsafeHtml);  // (B)
      } while (unsafeHtml !== parsedHtml);

  NIAT YANG DINYATAKAN (komentar baris 312-313)
  ---------------------------------------------
      "mXSS protection. Repeatedly parse the document to make sure it
       stabilizes, so that a browser trying to auto-correct incorrect HTML
       cannot cause formerly inert HTML to become dangerous."

  APA YANG SEBENARNYA TERJADI
  ---------------------------
  Urutan (A) lalu (B) membuat `parsedHtml` selalu dibaca dari elemen yang
  diparse dari `unsafeHtml` iterasi SEBELUMNYA, sedangkan `unsafeHtml` sudah
  dimajukan ke nilai berikutnya. Tulis P = parse, S = serialize:

      sebelum loop : inert = P(H0),  parsedHtml = H0
      iterasi 1    : unsafeHtml = H0
                     parsedHtml = S(inert) = S(P(H0)) = H1
                     inert      = P(H0)                    <- diparse ulang dari H0
                     uji: H0 != H1  -> lanjut
      iterasi 2    : unsafeHtml = H1
                     parsedHtml = S(inert) = S(P(H0)) = H1 <- SAMA dengan unsafeHtml
                     inert      = P(H1)
                     uji: H1 != H1  -> BERHENTI

  Pada iterasi ke-2, `parsedHtml` dan `unsafeHtml` dijamin identik SECARA
  KONSTRUKSI, karena keduanya sama-sama bernilai S(P(H0)). Kondisi keluar
  karena itu selalu terpenuhi di iterasi ke-2, apa pun masukannya.

  BUKTI DI PERAMBAN NYATA (Chromium 141) — bukan lagi simulasi abstrak
  --------------------------------------------------------------------
  Laporan pertama ditolak karena buktinya hanya simulasi JS dengan `transform`
  abstrak. Kini kode SANITIZER ASLI (port verbatim html_sanitizer.ts +
  inert_body.ts) dijalankan di Chromium 141 memakai DOMParser peramban sendiri,
  lewat Playwright. Perkakas: analysis/tools/mxss-browser/ (report.html,
  sanitizer.js, shot.mjs). Tangkapan layar: analysis/evidence/
  mxss-loop-real-chromium.png.

  Hasil terukur atas 32+ vektor (foreign content, raw-text element, dsb.):

  1. Loop yang DIKIRIM berputar MAKSIMAL 2 kali untuk SEMUA masukan.
     `maxBuggyIter = 2`. Anggaran 5 tidak pernah terpakai; galat "input is
     unstable" tidak pernah terlempar (`buggyEverThrew = false`).

  2. Ada masukan yang BENAR-BENAR butuh 3 ronde untuk stabil di Chromium nyata:
        <math><mtext><table><mglyph><style><img src=x onerror=alert(1)>   -> 3 ronde
        <ul><li><table><li>                                              -> 3 ronde
     Loop yang diperbaiki melakukan 3 iterasi; loop yang dikirim berhenti di 2,
     yakni SEBELUM titik stabil. Membuktikan ">=3 ronde" itu nyata, bukan teori.

  3. Ada masukan yang TIDAK PERNAH stabil di Chromium nyata:
        <plaintext><img src=x onerror=alert(1)>
     Setiap ronde parse menambah satu `</plaintext>` (rantai H0..H6 terukur,
     tumbuh tanpa batas). Loop yang DIPERBAIKI mendeteksi ini lalu MELEMPAR
     "input is unstable" (fail-closed). Loop yang DIKIRIM diam-diam kembali
     setelah 2 iterasi (fail-open) dan tidak pernah menyadarinya.

  Jadi galat "input is unstable" BUKAN mustahil secara prinsip — masukan
  peramban nyata memicunya. Cacatnya: loop versi rilis tidak akan pernah
  mencapai galat itu.

  TIGA AKIBAT YANG BISA DIVERIFIKASI
  ----------------------------------
  1. Jatah `mXSSAttempts = 5` tidak pernah terpakai habis (selalu tersisa 3).
  2. `throw new Error('...the input is unstable')` adalah KODE MATI —
     tidak ada masukan apa pun yang dapat mencapainya.
  3. Normalisasi berhenti setelah 2 parse, bukan pada titik stabil. Untuk
     rantai mutasi yang butuh >=3 ronde, serializer bekerja pada dokumen yang
     belum stabil.

  MENGAPA INI CACAT, BUKAN DESAIN
  -------------------------------
  Ketiga elemen ini hanya masuk akal bila penulis mengira loop dapat berputar
  lebih dari dua kali:
    - anggaran 5 percobaan (untuk apa, bila maksimum 2?)
    - pesan galat "input is unstable" (kapan bisa terjadi, bila selalu stabil?)
    - komentar "repeatedly parse ... to make sure it stabilizes"
  Jadi perilaku kode bertentangan dengan niat yang tertulis di kode itu sendiri.
  Ini definisi cacat, bukan trade-off yang dipilih.

  PERBAIKAN
  ---------
  Cukup MENUKAR dua pernyataan terakhir — parse dulu, baru baca hasilnya:

        unsafeHtml = parsedHtml;
        inertBodyElement = inertBodyHelper.getInertBodyElement(unsafeHtml);  // (B)
        parsedHtml = inertBodyElement.innerHTML;                             // (A)

  Diverifikasi pada simulasi yang sama (scratchpad/fix-check.mjs):
      tak pernah stabil : MELEMPAR -> 'input is unstable'   (benar)
      stabil ronde 3    : 3 iterasi, mencapai H2            (benar)
      sudah stabil      : 1 iterasi                         (benar, tidak berubah)

  DAMPAK KEAMANAN — PENILAIAN JUJUR (mengapa laporan pertama ditolak)
  ------------------------------------------------------------------
  Ini BUKAN XSS siap pakai, dan setelah pengujian peramban nyata saya justru
  MEMPERKUAT sikap itu, bukan melemahkannya. Diuji langsung: apakah keluaran
  loop yang cacat, saat DIPARSE ULANG peramban (seperti aplikasi menetapkan
  el.innerHTML), pernah menghasilkan simpul berbahaya (img[onerror]/script)?

      Battery 6+ vektor mXSS klasik -> `anyLiveDanger = false`.
      Contoh math/mtext: baik loop cacat maupun loop benar menghasilkan
      keluaran IDENTIK dan AMAN: `<img src="x">` (atribut onerror dibuang
      allowlist, apa pun jumlah rondenya).

  Sebabnya: langkah akhir `_sanitizeHtml` bukan meneruskan string mentah,
  melainkan `SanitizingHtmlSerializer.sanitizeChildren()` yang MEMBANGUN ULANG
  keluaran dari nol via allowlist (`VALID_ELEMENTS`/`VALID_ATTRS`) +
  `encodeEntities`. Benteng utama itu tetap utuh dan efektif TERLEPAS dari
  berapa ronde loop berputar. Itulah kemungkinan besar alasan tim keamanan
  menolak laporan pertama: tanpa eksploitasi tingkat-keluaran, loop yang rusak
  adalah regresi defense-in-depth, bukan kerentanan.

  APA YANG SESUNGGUHNYA TERBUKTI (dan layak dilaporkan)
  -----------------------------------------------------
  Bukan XSS. Yang terbukti di peramban nyata adalah: sebuah GARDA FAIL-CLOSED
  telah diam-diam menjadi FAIL-OPEN.
    - Niat kode: bila HTML tak kunjung stabil setelah 5 ronde, TOLAK (lempar).
    - Kenyataan: loop tak pernah mencapai ronde ke-3, sehingga masukan yang
      benar-benar tak stabil (`<plaintext>...`) LOLOS diam-diam alih-alih
      ditolak. Garda backstop-nya mati total (kode mati).
  Nilainya: garda mXSS ada justru sebagai jaring pengaman untuk saat asumsi
  serializer allowlist suatu hari tak berlaku (mis. elemen/atribut baru, bug
  peramban baru). Jaring itu kini bolong. Itu cacat keamanan yang sah untuk
  diperbaiki — dengan perbaikan 2 baris — meski hari ini belum bisa dieksploitasi.

  CAKUPAN TES
  -----------
  Satu-satunya tes bernama mXSS (html_sanitizer_spec.ts:292) sebenarnya menguji
  jalur `_sanitizeUrl`, bukan perilaku multi-ronde loop. Tidak ada tes yang
  menegaskan berapa kali loop berputar atau bahwa galat "unstable" dapat
  terjadi. Inilah sebabnya cacat ini tidak tertangkap.

  CATATAN PELAPORAN (untuk pengajuan ulang)
  -----------------------------------------
  Framing ulang yang disarankan saat mengajukan kembali ke security@angular.io:
  JANGAN mengklaim XSS. Ajukan sebagai "fail-closed mXSS guard rendered
  unreachable (dead code) — defense-in-depth regression", lampirkan tangkapan
  layar peramban nyata (analysis/evidence/mxss-loop-real-chromium.png) dan
  perkakas reproduksi (analysis/tools/mxss-browser/). Tekankan tiga fakta
  terukur: (1) loop <=2 iterasi selalu; (2) masukan 3-ronde nyata ada; (3)
  masukan tak-stabil nyata (<plaintext>) lolos diam-diam alih-alih ditolak.
  Perbaikan bersifat sepele (tukar dua baris) dan tanpa risiko regresi.

F-03  `srcset` diizinkan sanitizer HTML tetapi tidak diperlakukan sebagai URL
      BERKAS  : packages/core/src/sanitization/html_sanitizer.ts:79-89
      SIFAT   : inkonsistensi; dampak keamanan dapat diabaikan
==============================================================================

      URI_ATTRS  = 'background,cite,href,itemtype,longdesc,poster,src,xlink:href'
      HTML_ATTRS = '...,sizes,span,srclang,srcset,start,...'

  `src` ada di URI_ATTRS sehingga nilainya melewati `_sanitizeUrl`.
  `srcset` ada di HTML_ATTRS saja, sehingga LOLOS tanpa sanitasi URL —
  padahal isinya persis daftar URL, pada elemen yang sama.

  DAMPAK: dapat diabaikan. `srcset` hanya dipakai memuat gambar; skema seperti
  `javascript:` tidak dieksekusi di sana. Saya mencantumkannya bukan sebagai
  kerentanan melainkan sebagai inkonsistensi nyata: dua atribut dengan isi
  sejenis pada elemen sama diperlakukan berbeda tanpa alasan yang tertulis.

  Berdekatan, TODO lama yang belum dikerjakan di baris 198:
      // TODO(martinprobst): Special case image URIs for data:image/...
  Ini sejalan dengan pengamatan pada berkas tes `url_sanitizer_spec.ts`, yang
  hanya mendaftarkan `data:image/...`, `data:video/...`, `data:audio/...`
  sebagai URL sah — padahal implementasinya meloloskan SEMUA `data:`,
  termasuk `data:text/html`. Niat (tipe media aman saja) dan implementasi
  (semua tipe) tidak sama. Peramban modern memblokir navigasi tingkat atas ke
  `data:`, sehingga dampak praktisnya kecil.

F-04  Pembacaan `firstChild` pertama melewati pemeriksaan DOM clobbering
      BERKAS  : packages/core/src/sanitization/html_sanitizer.ts:133
      SIFAT   : inkonsistensi defensif; tidak dapat dieksploitasi
==============================================================================

  Baris 133 (masuk ke traversal):
      let current: Node = el.firstChild!;            // langsung, tanpa cek

  Baris 148 (menuruni anak berikutnya):
      current = getFirstChild(current)!;             // lewat cek clobbering

  `getFirstChild` sengaja dibuat untuk memvalidasi bahwa `.firstChild` tidak
  di-clobber (`isClobberedElement` memakai `compareDocumentPosition`). Semua
  penurunan lain memakainya; hanya pembacaan pertama yang tidak.

  TIDAK DAPAT DIEKSPLOITASI: `el` di sini adalah inert body element atau
  `<template>.content` (DocumentFragment). DOM clobbering bekerja lewat akses
  properti bernama pada `document` dan `HTMLFormElement`; keduanya tidak
  berlaku untuk kedua jenis simpul tersebut. Saya mencantumkannya hanya sebagai
  inkonsistensi yang sebaiknya dirapikan agar niat defensifnya seragam.

F-05  Validator APP_ID hanya ada di ngDevMode, sedangkan nilainya
      diinterpolasi TANPA escaping ke dalam <script> pada SSR PRODUKSI
      BERKAS  : packages/platform-server/src/utils.ts:171-177   (sink)
                packages/core/src/application/application_tokens.ts:55-70 (guard)
                packages/core/src/platform/platform_ref.ts:55        (guard dev-only)
                packages/core/src/application/create_application.ts:69 (guard dev-only)
      SIFAT   : guard dilucuti tepat pada mode build tempat nilainya berbahaya
==============================================================================

  SINK — interpolasi mentah ke literal string JS di dalam <script>
  ---------------------------------------------------------------
      const replayScriptContents =
        `window.__jsaction_bootstrap(` +
        `document.body,` +
        `"${appId}",` +                                   // <- MENTAH, tanpa escaping
        `${JSON.stringify(Array.from(regular))},` +       // <- tanpa escaping '<'
        `${JSON.stringify(Array.from(capture))}` +
        `);`;
      const replayScript = createScript(doc, replayScriptContents, nonce);

  `createScript` menetapkan `script.textContent = textContent`. Karena
  `<script>` adalah RAW TEXT ELEMENT, isinya diserialisasi apa adanya tanpa
  entity-escaping — sehingga `</script>` di dalamnya benar-benar menutup tag.

  GUARD YANG ADA — dan dilucuti di produksi
  -----------------------------------------
      // application_tokens.ts:55-70
      export const validAppIdInitializer: StaticProvider = {
        provide: ENVIRONMENT_INITIALIZER, multi: true,
        useValue: () => {
          const appId = inject(APP_ID);
          const isAlphanumeric = /^[a-zA-Z0-9\-_]+$/.test(appId);
          if (!isAlphanumeric) throw new RuntimeError(INVALID_APP_ID, ...);
        },
      };

  Regex itu allowlist ketat: tidak mengizinkan kutip, `<`, maupun backslash —
  bukti bahwa penulis SADAR nilai ini harus dibatasi. Tetapi pendaftarannya:

      platform_ref.ts:55        ...(ngDevMode ? [validAppIdInitializer] : []),
      create_application.ts:69  ...(ngDevMode ? [validAppIdInitializer] : []),

  Kedua call site membungkusnya dengan `ngDevMode`. Pada build produksi
  (termasuk SSR produksi) validator TIDAK ADA sama sekali.

  BUKTI (analysis/tools/appid-demo.mjs, replikasi persis template literal)
  -----------------------------------------------------------------------
      appId "x\";alert(document.domain);//"   -> ditolak dev, LOLOS produksi
        window.__jsaction_bootstrap(document.body,"x";alert(document.domain);//",["click"],[]);
                                                    ^ literal string JS tertutup dini

      appId "x</script><img src=x onerror=alert(1)>" -> ditolak dev, LOLOS produksi
        window.__jsaction_bootstrap(document.body,"x</script><img src=x onerror=alert(1)>",...);
                                                     ^ tag <script> tertutup, HTML menyusul

  INKONSISTENSI DENGAN BERKAS SAUDARA
  -----------------------------------
  `TransferState.toJson()` (core/src/transfer_state.ts:143-146) menulis ke
  jenis `<script>` yang SAMA dan meng-escape dengan sengaja:

      // Escape script tag to avoid break out of <script> tag in serialized output.
      return JSON.stringify(this.store).replace(/</g, '\\u003C').replace(/\//g, '\\u002F');

  Jadi basis kode ini TAHU aturannya dan menerapkannya di satu tempat, lalu
  melanggarnya di tempat lain yang konteksnya identik. Persis kelas cacat yang
  sama dengan F-01/F-02: kontrak yang dinyatakan sendiri tidak dipenuhi.

  PRASYARAT & PENILAIAN JUJUR
  ---------------------------
  Jalur ini hanya aktif bila:
    - SSR dipakai, DAN
    - event replay aktif (skrip event-dispatch disisipkan CLI —
      `if (eventDispatchScript)` pada utils.ts:169), DAN
    - build produksi (ngDevMode false, validator hilang)

  Yang TIDAK saya klaim: ini BUKAN kerentanan jarak jauh pada aplikasi biasa.
  `APP_ID` normalnya konstanta statis yang ditulis pengembang, bukan masukan
  pengguna. Untuk dieksploitasi, `APP_ID` harus berasal dari sumber yang bisa
  dipengaruhi penyerang — mis. server SSR multi-tenant yang menyetel APP_ID per
  tenant dari berkas konfigurasi atau variabel lingkungan. Itu mungkin, tetapi
  tidak umum.

  Yang saya klaim: ini cacat sejati. Sebuah guard yang dibuat KHUSUS untuk
  membatasi nilai ini dikompilasi keluar tepat pada satu-satunya mode build
  di mana nilai tersebut mencapai sink tanpa escaping. Perbaikannya ada dua
  pilihan, keduanya murah:
    (a) escape di sink — samakan dengan pola toJson():
        `"${appId.replace(/</g,'\\u003C').replace(/"/g,'\\"')}"` — atau lebih
        baik lagi pakai JSON.stringify(appId) alih-alih kutip manual, LALU
        escape `<`; atau
    (b) jadikan validator APP_ID selalu aktif (lepas dari ngDevMode) —
        biayanya satu regex sekali saat bootstrap.
  Opsi (a) lebih tepat karena memperbaiki sink, bukan hanya satu sumbernya;
  perhatikan bahwa nama event pada `JSON.stringify(...)` juga belum di-escape
  terhadap `<` di konteks raw-text yang sama.

F-06  Gate allowlist i18n dapat ditembus lewat rantai prototipe
      (akses bracket, bukan hasOwnProperty)
      BERKAS  : packages/core/src/render3/i18n/i18n_parse.ts:841
      SIFAT   : gate allowlist tidak sepenuhnya menutup; inkonsisten dengan
                baris 824 pada objek yang SAMA, berjarak 17 baris
==============================================================================

  KONTEKS
  -------
  i18n punya implementasi sanitasi HTML KEDUA yang terpisah dari
  `html_sanitizer.ts`: `parseIcuCase` (i18n_parse.ts:741) memarse isi pesan ICU
  memakai inert body, lalu `walkIcuTree` (:789) menyaringnya memakai
  `VALID_ELEMENTS`/`VALID_ATTRS` yang diimpor dari html_sanitizer.

  DUA GATE, DUA PERLAKUAN BERBEDA
  -------------------------------
      :824   if (VALID_ATTRS.hasOwnProperty(lowerAttrName)) {     // cabang binding — AMAN
      :841   } else if (VALID_ATTRS[lowerAttrName]) {             // cabang statis  — BOCOR

  `VALID_ATTRS` dibangun `tagSet`/`merge` (html_sanitizer.ts:18-32) memakai
  objek literal `{}`, BUKAN `Object.create(null)`. Rantai prototipe karena itu
  hidup, sehingga akses bracket mengembalikan nilai truthy untuk properti
  `Object.prototype`.

  BUKTI (analysis/tools/proto-bypass.mjs)
  ---------------------------------------
  Sepuluh nama menembus gate baris 841 sementara baris 824 menolaknya:
      constructor, toString, valueOf, hasOwnProperty, isPrototypeOf,
      propertyIsEnumerable, toLocaleString, __proto__,
      __defineGetter__, __lookupGetter__

  Untuk nama-nama itu `i18nResolveSanitizer` mengembalikan NONE (tidak ada di
  security schema), sehingga alur jatuh ke:
      addCreateAttribute(create, newIndex, attr.name, val);   // nilai MENTAH

  PENILAIAN JUJUR — mengapa dampaknya kecil
  -----------------------------------------
  Saya uji secara eksplisit apakah ada nama BERBAHAYA di rantai prototipe:
      onerror, onload, href, src, srcdoc, formaction, action, data, style
      -> tidak satu pun ada di Object.prototype
  Jadi yang lolos hanyalah nama atribut inert. `setAttribute('constructor', x)`
  tidak mengeksekusi apa pun. Ditambah lagi, pesan terjemahan pada mayoritas
  aplikasi adalah aset BUILD-TIME (berkas .xlf) yang tepercaya, bukan masukan
  pengguna runtime.

  Jadi ini BUKAN kerentanan. Yang membuatnya tetap layak dicatat: sebuah gate
  allowlist keamanan yang tidak menutup rapat, pada berkas yang sama dan objek
  yang sama dengan gate yang menutup rapat 17 baris di atasnya. Cukup ubah
  `VALID_ATTRS[lowerAttrName]` menjadi `VALID_ATTRS.hasOwnProperty(lowerAttrName)`
  — atau bangun set-set itu dengan `Object.create(null)` sehingga SELURUH pola
  akses bracket di basis kode ini menjadi aman sekaligus.

  CATATAN: pola akses bracket serupa ada di html_sanitizer.ts:199
  (`if (URI_ATTRS[lower])`), tetapi di sana AMAN karena sudah dijaga lebih dulu
  oleh `VALID_ATTRS.hasOwnProperty(lower)` pada baris 193, dan tidak ada nama
  `Object.prototype` yang menjadi anggota sah `VALID_ATTRS`.

F-08  UrlTree hasil parse tidak idempoten: dua URL berbeda menghasilkan pohon
      berbeda tetapi serialisasi yang SAMA
      BERKAS  : @angular/router DefaultUrlSerializer (parse/serialize)
      SIFAT   : kebingungan rute (route confusion)
      STATUS  : DAMPAK SUDAH DIUJI dengan Router sungguhan — TERBUKTI BERBEDA
      BUKTI   : analysis/evidence/f08-route-confusion.png
                analysis/tools/router-fuzz/impact.html
==============================================================================

  CARA DITEMUKAN
  --------------
  Fuzzer properti round-trip (analysis/tools/router-fuzz/fuzz-url.html),
  20.000 kasus, benih 20260731. Hasil: 16.769 stabil, 40 tidak stabil,
  0 gagal diparse ulang. Minimisasi otomatis mengerucutkan KEEMPAT PULUH
  ketidakstabilan ke satu bentuk: karakter tunggal `)`.

  PERILAKU TERUKUR
  ----------------
      parse(")")            -> root.children.primary.segments = [{path:"", ...}]
      serialize(itu)        -> "/"
      parse("/")            -> root.children = {}            <- TIDAK ADA anak
      serialize(itu)        -> "/"

  Jadi:
    - round-trip STRING stabil  : "/" -> "/" (konvergen langsung)
    - round-trip POHON TIDAK stabil: pohon-1 punya anak primary bersegmen kosong,
      pohon-2 tidak punya anak sama sekali.

  Cara lain menyatakan hal yang sama, dan ini bentuk yang lebih tajam:
      `)` dan `/` adalah dua URL BERBEDA yang menghasilkan UrlTree BERBEDA,
      tetapi keduanya menserialisasi ke string yang SAMA (`/`).

  Penyebabnya: `)` adalah pembatas penutup outlet. Sebuah `)` liar tanpa `(`
  pembuka menyisakan segmen kosong pada outlet primary, dan segmen kosong itu
  hilang saat diserialisasi — sehingga informasinya tidak dapat dipulihkan.

  PENILAIAN JUJUR
  ---------------
  Ini inkonsistensi normalisasi yang NYATA dan dapat direproduksi, tetapi saya
  TIDAK mengklaimnya sebagai kerentanan. Yang melemahkannya:
    - stringnya langsung konvergen ke `/`, jadi bilah alamat segera ternormalisasi
    - masukannya URL cacat (`)` liar), bukan bentuk yang muncul dari tautan wajar
    - tidak ada bukti batas keamanan terlewati

  LANGKAH SECURITY IMPACT — SUDAH DIKERJAKAN, DAN HASILNYA MENGUBAH VONIS
  -----------------------------------------------------------------------
  Diuji dengan Router SUNGGUHAN (bootstrapApplication + provideRouter), tabel
  rute berisi `''`, `'admin'`, dan `'**'`, masing-masing dengan guard pencatat
  yang merekam persis apa yang dilihatnya. Perbandingan dilakukan secara
  TERSTRUKTUR (rute yang cocok, segmen, data guard), bukan atas string.

      aspek                 navigasi ")"              navigasi "/"
      --------------------  ------------------------  --------------------
      router.url            "/"                       "/"        <- SAMA
      routeConfig.path      "**"  (wildcard)          ""  (rute kosong)
      UrlSegment daun       [{path:""}]               []
      guard yang berjalan   rute-wildcard             rute-kosong
      url yang dilihat guard [{path:""}]              []

  Kontrol positif: `/admin` mencocok ke rute `admin` — membuktikan harness ini
  memang mampu membedakan rute, sehingga hasil di atas bukan artefak alat buta.

  KESIMPULAN: `)` dan `/` MENCOCOK KE RUTE BERBEDA dan MENJALANKAN GUARD
  BERBEDA, padahal bilah alamat menampilkan `/` untuk keduanya.

  KONFOUND YANG SEMPAT MENYESATKAN (dicatat karena penting)
  ---------------------------------------------------------
  Percobaan pertama menunjukkan "perbedaan" yang TERNYATA PALSU: navigasi ke `/`
  mengembalikan false dengan guard kosong, karena router SUDAH berada di `/`
  akibat tes `)` sebelumnya — `navigateByUrl` menjadi no-op. Bila saya berhenti
  di situ, saya akan melaporkan artefak urutan tes sebagai temuan.
  Diperbaiki dengan mendahului setiap pengukuran dengan navigasi ke URL netral
  acak. Hasil di atas adalah hasil SETELAH perbaikan itu.

  PENILAIAN DAMPAK — JUJUR
  ------------------------
  Yang TERBUKTI: kebingungan rute. Satu URL yang tampil sebagai `/` di bilah
  alamat mengaktifkan rute wildcard, bukan rute `''`. Guard milik rute `''`
  TIDAK berjalan sama sekali.

  Yang BELUM terbukti, dan tidak saya klaim: eskalasi hak akses. Arah dampaknya
  bergantung konfigurasi aplikasi:
    - Bila rute `''` yang dijaga dan `**` tidak, penyerang yang mengirim tautan
      `)` membuat korban melewati guard rute `''` — tetapi yang dirender adalah
      komponen wildcard (biasanya halaman 404), sehingga umumnya bukan kebocoran.
    - Yang lebih layak dikhawatirkan: KETIDAKSESUAIAN SEBELUM/SESUDAH MUAT ULANG.
      Sebelum muat ulang aplikasi berada di rute `**`; setelah muat ulang bilah
      alamat berisi `/` sehingga aplikasi berada di rute `''`. Dua keadaan berbeda
      untuk satu alamat yang sama.
    - Menjadi serius hanya bila aplikasi menaruh logika keamanan pada rute `**`
      atau menyimpulkan otorisasi dari `router.url` (yang berbunyi `/`)
      alih-alih dari rute yang benar-benar aktif.

  KASUS DUNIA NYATA — DESINKRONISASI ANTAR-LAPISAN
  ------------------------------------------------
  Menelusuri "aplikasi nyata seperti apa yang terdampak" menghasilkan bentuk yang
  jauh lebih tajam daripada `)` vs `/`. Petunjuknya: `)` MEMOTONG sisa URL.

  Terukur (analysis/evidence/f08-crosslayer-desync.txt, tools/router-fuzz/):

  (1) Angular mencocokkan SEMUA varian ini ke rute `admin`, dan `router.url`
      menjadi `/admin` — sampahnya dibuang:
          /admin)     /admin)x     /admin)/y     /admin(     /admin)?q=1
      Dua kontrol membuktikan presisinya:
          /ADMIN)     -> wildcard  (pencocokan rute peka huruf besar-kecil)
          /admin%29   -> wildcard  (segmen literal "admin)"; jadi yang istimewa
                                    memang karakter `)` MENTAH, bukan bentuk
                                    ter-encode)

  (2) Peramban mengirim `)` MENTAH ke server (diverifikasi dengan server yang
      mencatat req.url):
          diminta "/admin)"   -> server menerima "/admin)"
          diminta "/admin)/y" -> server menerima "/admin)/y"
      `)` adalah sub-delim yang sah pada path (RFC 3986), jadi peramban tidak
      meng-encode-nya.

  (3) Pencocok path sisi-server yang lazim TIDAK menganggapnya `/admin`:
          req.path === '/admin'                          -> TIDAK cocok
          p === '/admin' || p.startsWith('/admin/')      -> TIDAK cocok
          nginx  location = /admin                        -> TIDAK cocok
          regex  ^/admin$                                 -> TIDAK cocok
          nginx  location /admin  (prefix)                -> cocok (satu-satunya)

  Jadi primitifnya: SATU URL yang oleh lapisan server dinilai BUKAN `/admin`,
  tetapi oleh router Angular dirender SEBAGAI rute `admin`.

  BENTUK APLIKASI YANG BENAR-BENAR RENTAN
  ---------------------------------------
  Yang dibutuhkan: otorisasi berbasis STRING PATH dilakukan di lapisan lain,
  DAN Angular merender rutenya. Itu berarti SSR/prerender, bukan SPA murni:

      // Express di depan Angular SSR — pola yang sangat lazim
      app.use((req, res, next) => {
        if (req.path === '/admin' || req.path.startsWith('/admin/')) {
          if (!isAuthed(req)) return res.status(403).send('Forbidden');
        }
        next();
      });
      app.get('*', angularSsrHandler);

  Permintaan `/admin)`:
    - middleware: req.path = "/admin)" -> tidak cocok -> PEMERIKSAAN AUTH DILEWATI
    - app.get('*') -> Angular SSR -> router mencocokkan rute `admin`
    - halaman admin dirender di server dan dikirim ke penyerang tanpa autentikasi

  Bentuk setara: aturan auth di CDN/WAF/reverse proxy atas path eksak, dan
  konfigurasi server-route @angular/ssr yang mencocokkan path secara harfiah.

  BATAS YANG HARUS DINYATAKAN
  ---------------------------
  - Pada SPA MURNI ini BUKAN bypass. Server memang menyajikan index.html untuk
    semua path, dan guard klien TETAP BERJALAN — terukur: `rute-admin` berjalan
    untuk `/admin)`. Jadi ini bukan bypass guard Angular.
  - Yang saya UKUR terpisah: (1) pencocokan rute Angular, (2) apa yang diterima
    server, (3) perilaku pencocok server. Yang saya SIMPULKAN, bukan jalankan
    ujung-ke-ujung: komposisi ketiganya pada aplikasi SSR nyata dengan middleware
    auth. Membangun aplikasi SSR berautentikasi sungguhan adalah langkah
    berikutnya yang belum dikerjakan.
  - Tanggung jawabnya bisa diperdebatkan: sebagian akan menyebut ini kesalahan
    aplikasi (jangan otorisasi berdasarkan string path). Bantahannya: Angular
    MENDIAMKAN karakter yang mengubah arti path, sehingga dua lapisan yang sama-
    sama masuk akal menjadi tidak sinkron. Menolak `)` liar, atau tidak
    memotongnya diam-diam, menutup seluruh kelas ini.

  Karena itu F-08 naik dari "inkonsistensi normalisasi" menjadi "desinkronisasi
  path antar-lapisan" — dengan jalur eksploitasi yang masuk akal dan komponennya
  terukur, tetapi komposisi ujung-ke-ujungnya belum didemonstrasikan.

  HIPOTESIS XSS — DIUJI DAN DIBANTAH
  ----------------------------------
  Pertanyaan wajar berikutnya: bila `)` memotong URL, bisakah sisa yang dipotong
  dipakai menyelundupkan muatan XSS? Diuji, dan jawabannya TIDAK. Tiga pengukuran
  menutup jalur itu (analysis/evidence/f08-xss-hypothesis-refuted.txt):

  (a) Peramban meng-encode metakarakter HTML pada path. Memuat
          /admin)"><img src=x onerror=alert(1)>
      membuat server menerima
          /admin)%22%3E%3Cimg%20src=x%20onerror=alert(1)%3E
      `"`, `<`, `>` menjadi %22/%3C/%3E. Jadi `<script>` mentah TIDAK dapat
      dikirim lewat path. (Bandingkan: `)` sendiri TIDAK di-encode — itulah
      sebabnya desinkronisasi path tetap berlaku, tetapi XSS tidak.)

  (b) Angular MENORMALKAN bilah alamat, termasuk pada MUAT LANGSUNG — bukan hanya
      navigasi klien. Terukur sebelum dan sesudah bootstrap:
          sebelum boot : location.pathname = "/admin)EVIL"
          sesudah boot : location.pathname = "/admin"
      Muatan lenyap dari `location`. Query dan fragment sesudah `)` ikut dibuang.

  (c) Tidak ada residu yang tersisa untuk dibaca aplikasi:
          location.search           -> ""
          location.hash             -> ""
          snapshot.queryParams      -> {}
          snapshot.fragment         -> null
          segmen                    -> ["admin"]
      Kontrol: `/admin?q=BERSIH#f` MEMPERTAHANKAN query dan fragment dengan benar,
      membuktikan pengukuran ini memang mampu melihat keduanya bila ada.

  Jadi bagian yang dipotong DIBUANG, bukan disimpan diam-diam di suatu tempat.
  Tidak ada bahan untuk XSS, dan tidak ada desinkronisasi `router.url` vs
  `location` di sisi klien — keduanya sepakat setelah bootstrap.

  CATATAN ZERO-TRUST YANG TETAP BERLAKU
  -------------------------------------
  Yang tersisa setelah XSS dibantah tetap satu hal, dan justru itu intinya:
  LAPISAN SERVER DAN LAPISAN ANGULAR MELIHAT PATH YANG BERBEDA untuk satu
  permintaan yang sama. Konsekuensi yang masuk akal tanpa perlu XSS:
    - otorisasi berbasis path di server/proxy/CDN dilewati (bagian sebelumnya)
    - log akses server mencatat `/admin)EVIL` sementara telemetri klien mencatat
      `/admin`; korelasi saat penyelidikan insiden menjadi tidak cocok
    - aturan WAF/rate-limit per-path dinilai atas string yang kemudian ditafsirkan
      ulang oleh Angular

  Ini kelas "otorisasi dilakukan di layer berbeda" — bukan kelas injeksi.

  Status rantai validasi sekarang:
      hipotesis YA | trace YA | neg-ctl YA | pos-ctl YA | runtime YA
      | security impact YA (terukur, terbatas) | repro independen YA

  DAMPAK — PENILAIAN JUJUR
  ------------------------
  Ini KETERSEDIAAN, bukan kerahasiaan atau integritas. Tidak ada kebocoran data

  analysis/evidence/f09-cookie-tossing-demo.txt, tools/xsrf/cookie-toss.mjs

      ---------------------------------------  -------------------  ---------
      1. sebelum serangan                      ""                   BERHASIL
      2. evil.contoh.test menyetel

      3. korban membuka app.contoh.test        "XSRF-TOKEN=%"       GAGAL
                                                                    URIError

  Yang penting pada demonstrasi ini:
    - Penyerang berada di ORIGIN BERBEDA (evil.contoh.test), bukan di origin
      korban. Tidak dibutuhkan XSS pada app.contoh.test.
    - Satu-satunya kemampuan yang dipakai adalah menyetel cookie ber-`Domain`
      pada domain INDUK — perilaku cookie yang normal dan tidak diblokir peramban
      (hanya prefiks `__Host-` yang mencegahnya, dan Angular tidak memakainya).
    - Langkah 1 adalah kontrol: tanpa cookie, POST BERHASIL. Jadi kegagalan pada
      langkah 3 benar-benar disebabkan cookie yang ditanam.

  MODEL ANCAMAN: "related-domain attacker" — penyerang menguasai SATU subdomain
  saudara. Ini model yang diakui dan nyata pada organisasi dengan subdomain

  ketiga, atau subdomain lama yang terbengkalai.

  Dampak akhir: penolakan layanan LINTAS-ORIGIN dan PERSISTEN atas seluruh

  menghapus cookie secara manual.

  PERBAIKAN
  ---------
  Bungkus decode-nya, dan putuskan sikap gagalnya secara sadar:

      if (cookieName.trim() === name) {
        try { return decodeURIComponent(cookieValue); }
        catch { return cookieValue; }   // atau null — tetapi JANGAN melempar
      }

  yang sudah ada di xsrfInterceptorFn, sehingga kegagalan ekstraksi token tidak
  pernah menggagalkan permintaan.

  KOREKSI ISTILAH: saya sempat menulis F-10 "lebih mudah dijangkau daripada

      F-10: satu halaman satu pengguna error sekali, lalu pulih sendiri

  PERBAIKAN
  ---------
  Jadikan codec baku toleran seperti URLSearchParams — decode dengan fallback:

  memang menghapus prasyarat lintas-origin yang tidak disengaja, TETAPI
  eksploitasinya tetap memerlukan DUA KONTEKS OTORISASI yang dapat dibedakan
  meminta URL yang sama dalam masa hidup cache Service Worker.

  Itu tidak harus dua orang berbagi komputer. Bentuk realistisnya:
    - logout Alice lalu login Bob
    - pergantian tenant atau organisasi
    - account switcher bawaan produk SaaS
    - admin melakukan impersonation lalu kembali ke akunnya
    - token berubah setelah role atau identitas diganti
    - satu pengguna dengan akun personal dan bisnis
    - kiosk atau workstation bersama

  ISTILAH YANG BENAR
  ------------------
  `Vary` BUKAN berarti "jangan cache". Artinya representasi ini dipilih
  berdasarkan nilai header permintaan tersebut, sehingga cache HARUS
  mempertimbangkan header itu saat mencari kecocokan. Default Cache API adalah
  `ignoreVary: false`. Rumusan yang dipakai di laporan: server menyatakan
  dengan benar bahwa representasi bervariasi menurut header Authorization;
  pencocokan baku peramban karena itu menolak respons Alice untuk permintaan
  Bob; Angular menimpa keputusan itu dengan ignoreVary: true.

  SEVERITY
  --------
  Medium adalah klaim paling defensif: kerahasiaannya konkret, tetapi dibatasi
  perlunya transisi identitas pada profil peramban yang sama. Bisa lebih tinggi
  bila account/tenant switching adalah alur normal produk, respons memuat data
  finansial/medis/token/PII sensitif, endpoint dipakai banyak tenant, penyerang
  dapat mengarahkan korban berganti akun, atau cache bertahan sesudah logout
  yang dianggap membersihkan sesi. Tidak diklaim tanpa bukti tambahan.

  USULAN
  ------
  Minimal:
      function buildCacheQueryOptions(
        inOptions?: Pick<CacheQueryOptions, 'ignoreSearch' | 'ignoreVary'>,
      ): CacheQueryOptions {
        return {ignoreVary: false, ...inOptions};
      }
  Bila `true` perlu dipertahankan demi kompatibilitas aset statis, pisahkan
  defaultnya: assetGroups boleh mempertahankan perilaku lama (isinya di-hash,
  tidak bergantung header), dataGroups default `false`.

  DILAPORKAN TERPISAH DARI F-12
  -----------------------------
  F-13 dikirim sebagai laporan keamanan MANDIRI, bukan subbagian F-12.
  Dokumentasi Angular mengakui pencocokan glob bersifat parsial, sehingga F-12
  lebih mungkin diperlakukan sebagai bug correctness; menggabungkannya berisiko
  menyeret turun F-13 yang jauh lebih kuat. Di laporan F-13, F-12 hanya disebut
  satu kalimat di bagian akhir.
    Laporan  : analysis/reports/F-13-ngsw-ignorevary.md
    Prosedur : analysis/reports/PENGIRIMAN-F13.md

  KENAPA BUKAN PERILAKU YANG DIRANCANG
  ------------------------------------
  Dokumentasi (adev/.../service-workers/config.md, bagian dataGroups.urls)
  hanya menyatakan "A list of URL patterns. URLs that match these patterns are
  cached according to this data group's policy." Tidak ada penyebutan bahwa
  pencocokannya substring, tidak ada bahwa pola path berlaku lintas-origin.
  Caching lintas-origin memang didukung — dengan menulis URL absolut (dokumen
  menyebut CDN seperti Google Fonts), bukan sebagai efek samping `/api/**`.

  PERBAIKAN
  ---------
  Menambahkan `^` saja TIDAK cukup — dan ini bagian penting dari laporannya.
  `data.ts` menguji URL absolut, sehingga pola path yang di-anchor
  (`^\/api\/.*$`) justru tidak akan pernah cocok.

  Perbaikan juga TIDAK BOLEH memaksa seluruh dataGroups menjadi same-origin:
  Angular memang mendukung caching data lintas-origin secara sengaja
  (dokumentasinya membahas respons opaque dan cacheOpaqueResponses). Usulan
  yang kompatibel:

    1. Pola yang diawali "/" dianggap path pada origin Service Worker.
    2. Pola yang memuat skema/origin, mis. "https://cdn.example/**", tetap
       diperlakukan sebagai pola lintas-origin seperti sekarang.
    3. Pencocokan bergaya path dilakukan terhadap pathname + search yang sudah
       dinormalkan, bukan terhadap seluruh URL absolut origin lain.

  Secara konsep, di data.ts:

      const parsed = new URL(req.url);
      if (configuredPattern.startsWith('/')) {
        if (parsed.origin !== adapter.origin) return false;
        return pattern.test(parsed.pathname + parsed.search);
      }
      return pattern.test(req.url);

F-14  Validators.pattern(string) membungkus pola dengan `^` dan `$` TANPA grup
      non-capturing -> alternasi tingkat atas lolos dari anchor
==============================================================================

  BERKAS
  ------
  packages/forms/src/validators.ts:569-596

      if (pattern.charAt(0) !== '^') regexStr += '^';
      regexStr += pattern;
      if (pattern.charAt(pattern.length - 1) !== '$') regexStr += '$';
      regex = new RegExp(regexStr);

  packages/forms/src/directives/validators.ts:695
      createValidator = (input) => patternValidator(input)   <- direktif [pattern]
                                                                memakai fungsi yang SAMA

  DUA CACAT DALAM SATU FUNGSI
  ---------------------------
  A. `|` punya presedensi TERENDAH dalam regex. `^cat|dog$` berarti
     `(^cat)|(dog$)`, bukan `^(cat|dog)$`. Alternatif di TENGAH
     (`admin|user|guest` -> `^admin|user|guest$`) tidak menyentuh `^` maupun
     `$` sama sekali, sehingga cocok sebagai SUBSTRING di mana pun.

  B. Pemeriksaan anchor memakai `charAt`, bukan parsing. Pola yang berakhir
     dengan dolar TER-ESCAPE (`\$`, artinya karakter dolar literal) dikira
     sudah ber-anchor, sehingga `$` tidak ditambahkan sama sekali.

  ACUAN — BUKAN SELERA SAYA
  -------------------------
  HTML Standard mendefinisikan atribut `pattern` pada <input> dikompilasi
  setara dengan membungkusnya: "^(?:" + pattern + ")$".
    https://html.spec.whatwg.org/multipage/input.html#the-pattern-attribute
  Dokumentasi Angular sendiri menyandingkan `Validators.pattern('[a-zA-Z ]*')`
  dengan `<input pattern="[a-zA-Z ]*">` sebagai padanan (validators.ts:380-386),
  dan Angular menyediakan direktif `[pattern]` yang memakai fungsi yang sama.
  Jadi peramban adalah acuan yang sah.

  Dokumentasi menyatakan MEKANISMENYA ("the `^` character is prepended and the
  `$` character is appended") tetapi tidak pernah memperingatkan bahwa alternasi
  membatalkan anchor itu. Berkas uji Angular sendiri
  (packages/forms/test/validators_spec.ts:389-441) hanya menguji kelas karakter
  — TIDAK ADA satu pun kasus dengan alternasi.

  RANTAI VALIDASI
  ---------------
  1. HIPOTESIS    Anchor yang dirangkai tanpa grup tidak mengikat alternasi.
  2. CODE TRACE   validators.ts:576-582; tidak ada `(?:` di mana pun.
  3. KONTROL POSITIF  pola tanpa alternasi berperilaku benar (5/5).
  4. KONTROL NEGATIF  `(cat|dog)` — developer yang kebetulan menulis kurung
                  sendiri TIDAK terdampak; `lizard` tetap ditolak. Pemicunya
                  spesifik, bukan "semuanya diterima".
  5. RUNTIME PROOF  Terhadap artefak npm @angular/forms@22.1.0:
                    analysis/tools/forms-pattern/probe.mjs
                      4 bypass alternasi, 2 bypass dolar-ter-escape
  6. PEMBANDING PLATFORM  Chromium, pola dan nilai yang sama dinilai dua kali —
                  `input.validity.patternMismatch` bawaan peramban vs
                  `Validators.pattern` Angular:
                    analysis/tools/forms-pattern/vs-platform.mjs
                    analysis/evidence/F-14-vs-platform.png
                    10 dari 24 kasus TIDAK SEPAKAT — SEMUANYA ke arah Angular
                    lebih longgar. Tidak ada satu pun kasus sebaliknya.

  CONTOH KETIDAKSEPAKATAN
  -----------------------
    pattern             value                  peramban   Angular
    cat|dog             "bulldog"              ditolak    DITERIMA
    cat|dog             "catastrophe"          ditolak    DITERIMA
    admin|user|guest    "abuserx"              ditolak    DITERIMA
    admin|user|guest    "no-user-here-really"  ditolak    DITERIMA

    jpg|png|gif         "jpg.exe"              ditolak    DITERIMA
    [0-9]+\$            "12$ dan lain-lain"    ditolak    DITERIMA

  DAMPAK — dengan disiplin yang sama seperti koreksi F-10
  -------------------------------------------------------
  Ini validasi formulir SISI KLIEN. Ia BUKAN batas otorisasi, dan penegakan
  yang otoritatif seharusnya di server. Saya tidak mengklaim lebih dari itu.

  Yang benar-benar didapat:
    1. Cacat kebenaran yang tidak ambigu: sintaks yang sama, dinilai berbeda
       dari platform yang ditirunya, dengan perbedaan SELALU ke arah lebih
       longgar.
    2. Bentuk bypass yang nyata bila pola dipakai sebagai allowlist sebelum
       sebuah sink (ekstensi berkas, nama peran, target pengalihan). Allowlist
       memang lazim ditulis dengan alternasi — itu bentuk paling alami untuk
       "salah satu dari".
    3. Developer tidak punya petunjuk bahwa ia salah: dokumentasi menyandingkan
       validator ini dengan atribut HTML yang berperilaku berbeda.

  Severity sebagai kerentanan: RENDAH. Sebagai cacat kebenaran: jelas, dengan
  perbaikan satu baris tanpa trade-off.

  PERBAIKAN
  ---------
      regexStr = `^(?:${pattern})$`;
  dan buang kedua pemeriksaan `charAt` — grup non-capturing membuatnya tidak
  perlu, sekaligus menutup cacat B. Ini juga menyelaraskan Angular dengan cara
  HTML Standard mengompilasi atribut `pattern`.

  CATATAN KOMPATIBILITAS: perubahan ini MENGETATKAN validasi. Aplikasi yang
  polanya memuat alternasi tingkat atas akan mulai menolak nilai yang tadinya
  diterima. Itu justru perbaikannya, tetapi layak disebut di catatan rilis.

  BAGAIMANA DITEMUKAN
  -------------------
  Bukan oleh pemindai. Setelah G-23 dan G-24 (lihat di bawah) habis, saya
  berpindah ke paket yang belum tersentuh — @angular/forms — dan mencari kelas
  yang sudah terbukti membayar di F-12: PERANGKAIAN ANCHOR. Pelajarannya: yang
  berpindah antar-area bukan regexnya, melainkan KELAS cacatnya.

      whitespace, sehingga normalizeSelector menghasilkan selektor CSS cacat
==============================================================================

  BERKAS
  ------
  packages/animations/browser/src/dsl/animation_ast_builder.ts
      :80   const SELF_TOKEN = ':self';
      :81   const SELF_TOKEN_REGEX = new RegExp(`s*${SELF_TOKEN}s*,?`, 'g');
      :589  const hasAmpersand = selector.split(/\s*,\s*/)      <- backslash BENAR di sini
      :593  selector = selector.replace(SELF_TOKEN_REGEX, '');

  Maksudnya tidak ambigu: buang `:self` beserta whitespace di sekitarnya dan
  koma yang menyertainya. EMPAT BARIS DI ATASNYA penulisnya menuliskan kelas
  whitespace dengan benar (`/\s*,\s*/`), jadi ia memang bermaksud whitespace —
  bukan huruf "s" literal.

  Yang benar-benar dibangun: /s*:selfs*,?/g — huruf "s" literal nol-atau-lebih,
  ":self", huruf "s" literal nol-atau-lebih, koma opsional. Tidak pernah
  memakan whitespace.

  Diverifikasi ADA di artefak npm: @angular/animations/fesm2022/browser.mjs:178.
  Sumber regex diambil programatik dari bundel, tidak diketik ulang.

  HASIL — peramban sebagai penilai
  --------------------------------
  analysis/tools/animations-selfregex/probe.mjs
  analysis/evidence/F-18-selfregex.png

  Selektor yang dihasilkan regex terkirim, dan vonis querySelectorAll:

      query(':self')              -> ""              DITOLAK (kosong)
      query(':self, .card')       -> " .card"        sah
      query(':self , .card')      -> " , .card"      DITOLAK SyntaxError
      query('.card, :self')       -> ".card, "       DITOLAK SyntaxError
      query('.card , :self')      -> ".card , "      DITOLAK SyntaxError
      query('.cards, :self')      -> ".cards, "      DITOLAK SyntaxError

  Benar secara semantik (sah DI PERAMBAN dan memilih himpunan elemen yang sama

  Kontrol negatifnya penting: bentuk yang paling lazim ditulis orang —
  `query(':self, .card')` — kebetulan SELAMAT. Itulah sebabnya cacat ini bisa
  bertahan lama tanpa terlihat.

  DUA KOREKSI ATAS USULAN PERBAIKAN SAYA SENDIRI
  ----------------------------------------------
  Datanya menolak saya dua kali, dan keduanya dicatat di harness:

  1. "Cukup tambahkan backslash" (/\s*:self\s*,?/g) -> 5/8. Masih meninggalkan
     koma menggantung pada urutan "X, :self", karena `,?` hanya ada SESUDAH
     token.
  2. "Serap koma di kedua sisi" (/\s*,?\s*:self\s*,?\s*/g) -> 7/8. Menghasilkan
     selektor yang SAH tetapi SALAH ARTI: `.card, :self, .row` menjadi
     `.card.row` — elemen yang punya KEDUA kelas, bukan salah satu. Uji
     "diterima peramban" saja TIDAK menangkap ini; perlu perbandingan himpunan
     elemen. Itulah sebabnya harness ini punya kolom semantik.

  PERBAIKAN YANG BENAR
  --------------------
  Bukan regex sama sekali. Pecah pada koma, buang token `:self`, gabungkan
  kembali — persis yang SUDAH dilakukan baris `hasAmpersand` empat baris di
  atasnya:

      const bagian = selector.split(/\s*,\s*/);
      const hasAmpersand = bagian.includes(SELF_TOKEN);
      if (hasAmpersand) {
        selector = bagian.filter((t) => t !== SELF_TOKEN && t !== '').join(', ');
      }

  Ini juga menghapus SELF_TOKEN_REGEX seluruhnya dan membuat kedua jalur
  memakai satu sumber kebenaran.

  DAMPAK — RENDAH, tanpa dimensi keamanan
  ---------------------------------------
  Selektor `query()` ditulis developer, bukan pengguna. Akibatnya
  `querySelectorAll` melempar SyntaxError saat animasi dijalankan, atau
  animasi diam-diam tidak mengenai elemen apa pun. Tidak ada dimensi keamanan:
  tidak ada masukan tak-tepercaya, tidak ada kebocoran, tidak ada eskalasi.

  BATAS BUKTI YANG DINYATAKAN
  ---------------------------
  `normalizeSelector` tidak diekspor, jadi harness ini MEREPRODUKSI fungsi itu
  (baris 588-603) alih-alih memanggilnya, lalu menyerahkan vonis selektornya
  kepada peramban sungguhan. Yang terbukti: regex terkirim (diambil dari
  bundel npm) + logika fungsi itu menghasilkan selektor yang ditolak
  querySelectorAll. Yang TIDAK saya amati langsung: lemparan dari dalam
  pipeline animasi Angular yang berjalan penuh.

F-21  encodeUriSegment melepas escape pada ':' — karakter yang dipakai
      parsernya sendiri sebagai pembatas nama outlet
==============================================================================

  BERKAS
  ------
  packages/router/src/url_tree.ts

      :513  function encodeUriString(s) {
              return encodeURIComponent(s)
                .replace(/%40/g, '@')
                .replace(/%3A/gi, ':')     <- ':' DIKEMBALIKAN jadi literal
                .replace(/%24/g, '$')
                .replace(/%2C/gi, ',');
            }

      :548  export function encodeUriSegment(s) {
              return encodeUriString(s)
                .replace(/\(/g, '%28')     <- '(' DIESCAPE, karena struktural
                .replace(/\)/g, '%29')     <- ')' DIESCAPE, karena struktural
                .replace(/%26/gi, '&');
            }

  Dalam satu ekspresi, dua karakter struktural diescape dan satu dilepas.
  Parser di berkas yang SAMA memakai ':' sebagai pembatas nama outlet:

      private parseParens(allowPrimary, depth) {
        ...
        if (path.indexOf(':') > -1) {
          outletName = path.slice(0, path.indexOf(':'));
        } else if (allowPrimary) {
          outletName = PRIMARY_OUTLET;
        }

  Serializer TIDAK menuliskan awalan `k:` untuk outlet primer di dalam kurung
  (serializeSegment, cabang non-root), sehingga titik dua PERTAMA yang ditemui
  parser di posisi itu berasal dari DATA, bukan dari sintaks.

  SIFAT YANG DIUJI, DAN SIFAT YANG SALAH SAYA PILIH LEBIH DULU
  ------------------------------------------------------------
  Ukurannya bukan spesifikasi luar: serializer dan parser adalah kelas yang
  sama, `DefaultUrlSerializer`. Serializer yang keluarannya tidak bisa dibaca
  ulang oleh parsernya sendiri salah menurut ukurannya sendiri.

  Sifat pertama yang saya uji — "pohon hasil round-trip identik" — TERLALU
  LEBAR, dan kontrol negatifnya yang membongkarnya. Dengan ukuran itu
  `/p/(a%3Ab)` ikut gagal, dan saya nyaris memasukkannya ke temuan. Ternyata
  `/p/(ab)`, tanpa titik dua sama sekali, gagal dengan cara yang persis sama:
  grup kurung berisi satu anak primer memang DIRATAKAN ke induknya. Normalisasi
  yang disengaja, tidak ada hubungannya dengan titik dua.

  Sifat yang benar-benar membedakan: MUNCULNYA NAMA OUTLET BARU. Perataan
  kurung tidak pernah memunculkan nama baru; cacat ini memunculkannya, dan
  namanya diambil dari data pengguna. Kedua baris itu SENGAJA dipertahankan di
  tabel probe, ditandai sebagai normalisasi yang diketahui.

  RUNTIME PROOF — artefak npm @angular/router@22.1.0
  --------------------------------------------------
  analysis/tools/router-colon/probe.mjs   (exit 0 = terkonfirmasi)

    /p/(a%3Ab//aux:x)      -> /p/(a:b//aux:x)
                              outlet {aux,primary} -> {a,aux,primary}
    /p/(admin%3Adash//aux:x) -> /p/(admin:dash//aux:x)
                              outlet {aux,primary} -> {admin,aux,primary}

  KONTROL NEGATIF — semuanya round-trip dengan BENAR:
    '(' dan ')' terenkode   -> diescape encodeUriSegment, utuh
    '/' dan ';' terenkode   -> dibiarkan %2F / %3B, utuh
    ':' di segmen biasa     -> utuh (di luar kurung ':' tidak struktural)
    ':' di outlet BERNAMA   -> utuh (awalan `k:` sudah memakan titik dua pertama)
    tanpa ':' sama sekali   -> utuh

  Jadi pemicunya bukan "kurung merusak segalanya", melainkan satu karakter di
  satu posisi. Dan fungsi yang SAMA membuktikan penulisnya tahu aturannya:
  ia mengescape '(' dan ')' tepat karena keduanya struktural.

  KETERJANGKAUAN — dibangun dari DATA, bukan dari URL yang dibuat-buat
  --------------------------------------------------------------------
  Bagian kedua probe tidak berangkat dari string URL sama sekali. Ia membangun
  UrlTree lewat kelas publik (UrlTree/UrlSegment/UrlSegmentGroup) — yang sama
  dengan yang dibangun `Router.createUrlTree` — lalu menyerahkannya ke
  serializer:

    nilai "laporan"     -> /p/(laporan//aux:x)     outlet utuh   (kontrol)
    nilai "admin:dash"  -> /p/(admin:dash//aux:x)  outlet {aux,primary}
                                                   -> {admin,aux,primary}
                                                   segmen primer HILANG

  Nilai penggunanya tidak pernah menyentuh sintaks URL; ia hanya sebuah string
  di dalam sebuah segmen. Serializer sendiri yang menjadikannya sintaks.

  DAMPAK — RENDAH sebagai kerentanan, jelas sebagai cacat kebenaran
  -----------------------------------------------------------------
  Yang saya klaim: URL yang ditulis aplikasi ke address bar tidak bisa dibaca
  ulang menjadi pohon yang sama. Setelah reload, back, atau berbagi tautan,
  rute yang aktif berbeda dari yang dinavigasikan: segmen outlet primer hilang,
  dan sebuah outlet bernama-dari-data muncul menggantikannya.

  Yang TIDAK saya klaim: ini bukan jalan penyerang-ke-korban dengan sendirinya.
  Outlet baru itu hanya benar-benar aktif bila konfigurasi rute aplikasi
  kebetulan punya outlet dengan nama tersebut, dan guard aplikasi tetap
  berjalan atas pohon hasil parse. Yang pasti terjadi tanpa syarat tambahan
  adalah HILANGNYA segmen primer yang dimaksud.

  PRASYARAT, dinyatakan terus terang:
    (a) aplikasi memakai outlet tambahan (auxiliary outlet), DAN
    (b) sebuah nilai yang dipengaruhi pengguna mendarat di segmen PERTAMA
        grup primer di dalam kurung.

  PERBAIKAN
  ---------
  Perlakukan ':' seperti '(' dan ')' sudah diperlakukan — pada posisi tempat ia
  struktural. Yang paling sempit: jangan lepas escape %3A untuk segmen, yaitu
  pindahkan `.replace(/%3A/gi, ':')` dari `encodeUriString` (dipakai bersama
  oleh query dan segmen) ke `encodeUriQuery` saja, tempat ':' memang tidak
  struktural. Query dan fragment tidak berubah perilakunya.

  Catatan: ini mengubah bentuk URL yang dihasilkan untuk segmen yang memuat
  ':' , jadi bukan perubahan yang tak kasat mata — perlu dinilai sebagai
  perubahan perilaku, bukan sekadar tambalan.

  BUKAN untuk proses keamanan. Ini cacat kebenaran; jalur yang tepat adalah
  isu publik, bukan security@angular.io.

  AREA YANG SUDAH DIPERIKSA DAN TERNYATA BENAR (perluasan cakupan)
  ----------------------------------------------------------------
  Setelah cakupan diperlebar melampaui html_sanitizer.ts, sembilan permukaan
  keamanan lain diperiksa dan TIDAK ditemukan cacat:
    - TransferState.toJson()      escape `<` dan `/` dengan benar; `<script>`
                                  raw-text tidak bisa ditembus
    - xsrfInterceptorFn           cek same-origin benar (URL relatif di-resolve
                                  dulu); `catch` gagal ke arah aman
    - enforceIframeSecurity       membersihkan src/srcdoc lalu melepas node;
                                  ɵɵvalidateAttribute fail-closed (throw)
    - resolveElement / '#host'    sinkron: tag dipasok tNode.value, '#host'
                                  memicu pembacaan tag asli dari DOM
    - SVG_ANIMATION_SENSITIVE_*   entri yang hilang jatuh ke throw -> LEBIH
                                  ketat, bukan lebih lemah
    - Router (RouterLink)         selector '[routerLink]' generik -> konteks
                                  komposit -> ɵɵsanitizeUrlOrResourceUrl yang
                                  meresolusi tag saat runtime; pada <a> menjadi
                                  ɵɵsanitizeUrl sehingga `javascript:` diblokir
    - @angular/elements           attributeChangedCallback memakai akses bracket
                                  (`attributeToPropertyInputs[attrName]!`) TETAPI
                                  ter-gate: observedAttributes = Object.keys(...)
                                  hanya memuat properti own, jadi peramban tidak

    - Hidrasi (ngh)               nilai atribut ngh hanya di-split '|' lalu

    - i18n: elemen tak valid      DIBUANG total beserta seluruh anaknya (rekursi
