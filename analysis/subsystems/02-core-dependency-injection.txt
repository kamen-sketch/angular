SUBSISTEM 02 :: Dependency Injection (@angular/core)
Lokasi   : packages/core/primitives/di/, packages/core/src/di/, packages/core/src/render3/di.ts
Status   : SELESAI DIANALISIS (jalur utama runtime)
==============================================================================

RINGKASAN ARSITEKTUR
--------------------
Angular punya DUA hierarki injector yang berbeda, dan kunci memahami DI adalah
memahami kapan masing-masing dipakai:

  A. EnvironmentInjector (R3Injector)   -> hierarki "aplikasi", di luar pohon DOM
     root -> platform -> aplikasi -> route-level -> lazy module
  B. NodeInjector                       -> hierarki "elemen", mengikuti pohon DOM
     satu injector per elemen yang punya directive/provider

Pencarian token selalu: NodeInjector (naik pohon elemen) -> EnvironmentInjector
(naik hierarki modul) -> NullInjector (lempar NG0201).

TIGA LAPIS KODE
---------------
1. `primitives/di` - kontrak minimal (`Injector.retrieve`, `NotFound`,
   `getCurrentInjector`/`setCurrentInjector`). Dipisah agar paket lain bisa
   memakai DI tanpa menarik seluruh core.
2. `src/di` - implementasi EnvironmentInjector, provider resolution, `inject()`,
   forwardRef, InjectionToken, dan JIT compiler untuk `@Injectable`.
3. `src/render3/di.ts` - NodeInjector: DI berbasis bloom filter di dalam LView.

MEKANISME PENTING
-----------------
* KONTEKS INJEKSI. `inject()` tidak menerima injector sebagai argumen; ia
  membaca variabel modul `_currentInjector` (di primitives) atau delegasi
  `_injectImplementation` (di inject_switch.ts). Setiap tempat yang "membuka"
  konteks injeksi memakai pola save/restore try-finally yang sama:
  `setCurrentInjector` + `setInjectImplementation`. Karena itu `inject()` hanya
  sinkron - setelah `await`, stack frame-nya sudah kehilangan konteks.

* SWITCH IMPLEMENTASI. `ɵɵinject` memanggil `getInjectImplementation() ||
  injectInjectorOnly`. Saat runtime sedang membuat directive, implementasinya
  diganti ke `directiveInject` (render3) sehingga token dicari lewat
  NodeInjector; di luar itu hanya EnvironmentInjector yang dilihat. Trik ini
  menjaga `src/di` tetap bebas dari ketergantungan render3 (tree-shaking).

* R3Injector.records. Setiap token dipetakan ke `Record{factory, value, multi}`.
  - `NOT_YET` = belum diinstansiasi, `CIRCULAR` = sedang diinstansiasi
    (dipakai untuk mendeteksi dependensi melingkar).
  - `value === null` record disimpan sebagai penanda "sudah dicari, tidak ada"
    agar pencarian tree-shakable provider tidak diulang.
  - Instansiasi = `hydrate()`; nilai yang punya `ngOnDestroy` otomatis
    didaftarkan ke `_ngOnDestroyHooks`.
  - Seluruh instansiasi dibungkus `setActiveConsumer(null)` supaya pembacaan
    signal di dalam factory TIDAK terlacak sebagai dependensi reaktif.

* providedIn (tree-shakable providers). Jika token tidak punya record,
  `R3Injector.get` melihat `ɵprov.providedIn` dan mencocokkannya dengan
  `this.scopes` (`'root'`, `'platform'`, `'environment'`, `'any'`) atau dengan
  `injectorDefTypes` (untuk `providedIn: SomeModule`). Inilah alasan service
  `providedIn:'root'` yang tak pernah di-inject bisa hilang dari bundle.

* limp mode (`injectRootLimpMode`). Bila belum ada injector sama sekali, token
  `providedIn:'root'` masih bisa dibuat dan nilainya disimpan langsung pada
  definisi injectable. Dipakai pada kode yang berjalan sebelum bootstrap.

* PROVIDER TREE. `walkProviderTree` menelusuri `imports` NgModule dan
  dependensi komponen standalone secara rekursif, dengan `dedup` set (mencegah
  modul diproses dua kali) dan `parents` array (mendeteksi impor melingkar).
  `importProvidersFrom` adalah pintu publiknya.

* PESAN ERROR. Jalur error DI menarik: `R3Injector.get` menangkap error
  CYCLIC_DI_DEPENDENCY / PROVIDER_NOT_FOUND, menambahkan token saat ini ke
  jalur dependensi (`prependTokenToDependencyPath`), lalu melempar ulang.
  Rangkaian token baru diformat menjadi pesan lengkap di frame paling atas
  (`augmentRuntimeError`). Di prod, semua ini diganti error kode saja - dan
  komentar di kode menjelaskan mengapa memakai `if (ngDevMode)` alih-alih
  early return (ESBuild lebih andal mem-tree-shake pola tersebut).

NODE INJECTOR: BLOOM FILTER
---------------------------
NodeInjector tidak menyimpan Map token->provider. Sebagai gantinya setiap node
injector menempati 9 slot di LView/TView.data: 8 slot bilangan 32-bit sebagai
BLOOM FILTER (256 bit) + 1 slot pointer ke parent.

  - `bloomAdd`: setiap token/directive diberi ID unik (`__NG_ELEMENT_ID__`),
    di-mask ke 0..255, lalu bit-nya dinyalakan di bucket
    `injectorIndex + (hash >> 5)`.
  - `bloomHasToken`: cek satu bit. Karena bloom filter, "true" berarti MUNGKIN
    ada (perlu verifikasi), "false" berarti PASTI tidak ada - inilah yang
    membuat penelusuran ke atas bisa dipotong lebih awal.
  - Ada DUA bloom per node: bloom milik node sendiri (di `tView.data`) dan
    bloom KUMULATIF (di `lView`) yang merupakan OR dari bloom seluruh leluhur.
    Bloom kumulatif memungkinkan `lookupTokenUsingNodeInjector` berhenti total
    saat leluhur pun dipastikan tidak punya token itu.
  - Verifikasi sebenarnya dilakukan `locateDirectiveOrProvider`, yang memindai
    rentang indeks provider dan directive milik TNode.

Aturan visibilitas yang diimplementasikan di `searchTokensOnInjector`:
  - `viewProviders` hanya terlihat oleh komponen itu sendiri dan turunan di
    dalam TEMPLATE-nya, bukan oleh konten yang di-project. Ini diputuskan lewat
    `canAccessViewProviders` (bandingkan `previousTView` vs `currentTView`).
  - Flag `@Host` dibatasi lewat `hostTElementNode` + `isHostSpecialCase`.
  - `@Self`/`@SkipSelf` dipetakan ke bit `InternalInjectFlags` dan diperiksa di
    `shouldSearchParent`.

Lintas-view: `getParentInjectorLocation` mengembalikan nilai terkemas berisi
(indeks injector, jumlah view yang harus dinaiki). Untuk embedded view yang
disisipkan di tempat lain, pencarian mengikuti DECLARATION_VIEW (tempat
template ditulis), bukan tempat DOM-nya disisipkan - sesuai semantik Angular.

`lookupTokenUsingEmbeddedInjector` menangani `createEmbeddedView(..., injector)`
: karena injector tambahan ini tidak punya bloom filter, pencarian dilakukan
node demi node dengan flag `Self` pada tiap tingkat.

CATATAN LAIN
------------
* `ɵɵgetInheritedFactory` menaiki rantai prototipe untuk menemukan factory milik
  kelas induk; dibungkus `noSideEffects` agar tidak menghalangi tree-shaking.
* `forwardRef` menandai fungsi dengan properti `__forward_ref__`; setiap titik
  yang membaca token memanggil `resolveForwardRef` sebagai identity function
  jika bukan forward ref.
* `injectAttributeImpl` membaca atribut statis dari array `tNode.attrs` yang
  memakai penanda (`AttributeMarker`) untuk memisahkan atribut biasa,
  namespaced, binding, dan template.
