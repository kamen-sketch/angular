GAMBARAN BESAR
--------------
Change detection (CD) Angular modern punya tiga lapis yang harus dibedakan:

  1. PENANDAAN (marking)   - siapa yang kotor. Menyalakan bit di LView[FLAGS].
  2. PENJADWALAN (scheduling) - kapan tick dijalankan. ChangeDetectionScheduler.
  3. PENELUSURAN (traversal) - bagaimana pohon view dikunjungi. refreshView dkk.

Sinyal, event listener, `markForCheck`, `async` pipe, dan `setInput` semuanya
hanya melakukan (1) + memberi notifikasi ke (2). Pekerjaan sesungguhnya di (3).

FLAG PADA LView (LViewFlags) YANG MENGGERAKKAN SEMUANYA
--------------------------------------------------------
  CheckAlways            view dengan strategi Default (selalu dicek saat Global)
  Dirty                  ditandai kotor (OnPush yang perlu dicek)
  RefreshView            "segarkan view INI saja" - dipakai untuk view
                         transplanted dan view yang signal-nya berubah
  HasChildViewsToRefresh penanda jalur: ada keturunan yang perlu disegarkan
  Attached / Destroyed / IsRoot / SignalView / HasI18n / HasEmbeddedViewInjector

Perbedaan `Dirty` vs `RefreshView` adalah inti desain zoneless:
  - `Dirty` hanya dihormati pada mode Global.
  - `RefreshView` dihormati di SEMUA mode, termasuk Targeted.
`markViewDirty` memilih bit mana yang dipakai berdasarkan `isRefreshingViews()`:
saat CD sedang berjalan hanya `Dirty` (agar tidak memicu re-entrancy), saat di
luar CD keduanya (agar bisa menjalankan ulang CD secara sinkron).

Penandaan selalu berpasangan: node yang kotor + SELURUH LELUHURNYA diberi
`HasChildViewsToRefresh` (`markAncestorsForTraversal`). Penelusuran berhenti
lebih awal ketika menemukan leluhur yang sudah bertanda - optimasi penting agar
menandai 1000 komponen tidak berarti 1000 kali jalan ke root.

DUA MODE PENELUSURAN
--------------------
  ChangeDetectionMode.Global   : segarkan CheckAlways + Dirty + RefreshView
  ChangeDetectionMode.Targeted : HANYA RefreshView / consumer signal yang kotor

Aplikasi zoneless praktis selalu berjalan dalam mode Targeted. Aplikasi berbasis
zone memakai Global (lihat `ApplicationRef.tick` yang menyalakan
`ViewTreeGlobal` saat `!zonelessEnabled`).

`detectChangesInView` adalah tempat keputusan dibuat. Perhatikan urutannya:
flag dibersihkan SEBELUM `refreshView` dipanggil, sehingga view boleh
menandai dirinya kotor lagi selama refresh (dan akan tertangkap oleh loop
berikutnya). Jika view tidak perlu disegarkan tapi punya
`HasChildViewsToRefresh`, penelusuran turun dalam mode Targeted dengan
`setActiveConsumer(null)` agar konteks reaktif induk tidak bocor ke bawah.

URUTAN BAKU DI refreshView (jangan pernah diubah tanpa alasan kuat)
-------------------------------------------------------------------
  1.  enterView + siapkan reactive consumer
  2.  reset flag pre-order hook, reset bindingIndex
  3.  jalankan template dalam RenderFlags.Update  <-- semua binding dievaluasi
  4.  pre-order hooks: ngOnChanges, ngOnInit, ngDoCheck
  5.  tandai transplanted views (markTransplantedViewsForRefresh)
  6.  jalankan view effects (runEffectsInView)
  7.  segarkan embedded views (Global)
  8.  refresh content queries -> content hooks (AfterContentInit/Checked)
  9.  host bindings (processHostBindingOpCodes)
  10. segarkan komponen anak (Global)
  11. view queries -> view hooks (AfterViewInit/Checked)
  12. matikan firstUpdatePass, jalankan EFFECTS_TO_SCHEDULE
  13. daftarkan afterRender sequences, bersihkan flag Dirty/FirstLViewPass

Alasan urutan tertentu didokumentasikan langsung di kode:
  - Content query harus di-refresh SEBELUM content hooks (hasil query harus
    valid saat ngAfterContentInit).
  - View query dieksekusi SETELAH komponen anak disegarkan, karena template di
    view ini bisa saja disisipkan ke dalam komponen anak.
  - `tView.firstUpdatePass = false` sengaja TIDAK di blok finally: jika terjadi
    exception, instruksi styling belum sempat mendaftarkan diri ke linked list,
    sehingga flag harus tetap true agar percobaan berikutnya benar.
  - Saat error, `markAncestorsForTraversal` dipanggil ulang karena flag jalur
    sudah terlanjur dibersihkan - tanpa ini view kotor bisa jadi tak terjangkau.
  - Ada peringatan "PERF WARNING: do NOT extract this to a separate function"
    di tiga blok hook - inlining disengaja demi hasil benchmark.

INTEGRASI SIGNAL: REACTIVE LVIEW CONSUMER
-----------------------------------------
Setiap view (kecuali embedded) punya satu `ReactiveLViewConsumer` - node
consumer dari subsistem 01 yang mewakili template. Saat template dieksekusi,
consumer ini menjadi `activeConsumer`, sehingga setiap signal yang dibaca
template otomatis menjadi dependensinya. Ketika signal berubah,
`consumerMarkedDirty` -> `markAncestorsForTraversal(lView)`.

Detail yang menarik:
  - Consumer di-POOL (`freeConsumers`) dan hanya "committed" ke LView bila
    template benar-benar membaca signal (`consumerOnSignalRead` yang memasang
    dirinya ke `lView[REACTIVE_TEMPLATE_CONSUMER]`). Template tanpa signal tidak
    membayar biaya alokasi apa pun.
  - Embedded view TIDAK punya consumer sendiri; mereka berbagi dengan view
    komponen, sehingga granularitas CD berbasis signal adalah PER KOMPONEN.
    Komentar di `viewShouldHaveReactiveConsumer` menjelaskan bahwa granularitas
    per-view tinggal mengubah kondisi di fungsi itu.
  - `TEMPORARY_CONSUMER_NODE` menangani kasus langka
    `viewContainerRef.createEmbeddedView(...).detectChanges()`, di mana CD
    dijalankan langsung pada view yang seharusnya tidak punya consumer.

PENJADWALAN (ChangeDetectionSchedulerImpl)
------------------------------------------
`notify(source)` memetakan sumber notifikasi menjadi bit `dirtyFlags` di
ApplicationRef, lalu menjadwalkan satu tick jika belum ada:
  MarkAncestorsForTraversal / DeferBlockStateUpdate -> ViewTreeTraversal
  MarkForCheck / Listener / SetInput               -> ViewTreeCheck
  RootEffect                                       -> RootEffects
  RenderHook / ViewAttached / dll                  -> AfterRender saja

Poin penting:
  - Penjadwalan memakai `scheduleCallbackWithRafRace` (balapan antara
    requestAnimationFrame dan setTimeout) supaya tetap jalan di tab background
    maupun saat rAF tidak tersedia.
  - Setelah satu tick, scheduler beralih sementara ke microtask
    (`switchToMicrotaskScheduler`) agar perubahan yang dipicu `Promise.resolve`
    (mis. NgModel) masih masuk ke frame paint yang sama.
  - Tanpa zoneless, notifikasi dari `Listener` diabaikan (kompatibilitas mundur:
    zone yang akan menjalankan CD).
  - Tick didaftarkan sebagai pending task (`PendingTasksInternal`) sehingga
    `whenStable`/SSR tahu aplikasi belum diam.
  - `shouldScheduleTick` menolak jadwal ganda dan menolak menjadwal saat kita
    masih di dalam Angular zone pada aplikasi berbasis zone.

LOOP SINKRONISASI DI ApplicationRef
-----------------------------------
`_tick` -> `synchronize` -> `synchronizeOnce` berulang selama `dirtyFlags`
belum kosong, maksimum MAXIMUM_REFRESH_RERUNS (10) sebelum melempar
"Infinite change detection". Satu putaran `synchronizeOnce`:
  1. flush root effects
  2. jika ada bit ViewTree*, telusuri `allViews` (Global atau Targeted)
  3. jika masih ada view kotor atau root effect -> return lebih awal (loop lagi)
  4. jalankan afterRender hooks
  5. `syncDirtyFlagsWithViews` menyelaraskan bit dengan keadaan view nyata

Di dalam satu view, `detectChangesInViewWhileDirty` juga punya loop sendiri
dengan batas MAXIMUM_REFRESH_RERUNS (100) khusus mode Targeted.

Mode dev menambah `checkNoChanges` pass (asal ExpressionChangedAfterItHasBeenCheckedError).
Mode `Exhaustive` menelusuri semua view, bukan hanya yang kotor.
