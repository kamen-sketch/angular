SUBSISTEM 11 :: Hydration & SSR
Lokasi   : packages/core/src/hydration/**, packages/platform-server/**,
           packages/ssr/**, packages/core/src/transfer_state.ts
Status   : DIANALISIS - anotasi server, klaim node klien, event replay,

==============================================================================

MASALAH YANG DIPECAHKAN
-----------------------
Tanpa hidrasi, aplikasi SSR akan MENGHANCURKAN seluruh DOM hasil server lalu
merender ulang dari nol (destructive hydration) - menyebabkan kedipan dan
kehilangan status DOM. Dengan hidrasi, runtime klien MENGKLAIM node DOM yang
sudah ada alih-alih membuatnya.

Agar bisa mengklaim, klien harus tahu STRUKTUR view yang dirender server.
Informasi itu dikirim lewat TransferState dengan kunci `NGH_DATA_KEY` (dan
`NGH_DEFER_BLOCKS_KEY` untuk blok @defer), sementara setiap host komponen di
HTML diberi atribut `ngh="<index>"` yang menunjuk ke entri data tersebut.

SISI SERVER: ANOTASI
--------------------
`annotateForHydration(appRef, doc)` dijalankan setelah render selesai:
  - menelusuri semua `appRef._views`, mengambil LView/LContainer akarnya,
  - `serializeLView` merekam per node: jumlah node akar, indeks node yang
    "disconnected", teks kosong yang perlu penanda, jalur node yang tidak bisa
    ditemukan lewat penelusuran biasa (`conditionallyAnnotateNodePath`),
  - `serializeLContainer` merekam view di dalam container beserta `ssrId`
    TView-nya sehingga klien tahu template mana yang harus dipakai,
  - mengumpulkan jenis event yang perlu di-replay,
  - `insertCorruptedTextNodeMarkers` menyisipkan komentar penanda untuk teks
    kosong/berdampingan yang akan hilang saat parsing HTML,
  - hasilnya disimpan ke TransferState. Catatan penting di kode: kunci hidrasi
    SELALU ditulis walau daftar view kosong, sebagai sinyal ke klien bahwa
    server memang menjalankan hidrasi.

Node yang tidak bisa dihidrasi ditandai agar dilewati: komponen dengan
ShadowDom encapsulation, node yang diproyeksikan dari tempat lain, dan subtree
ber-atribut `ngSkipHydration`.

SISI KLIEN: KLAIM NODE
----------------------
`withDomHydration()` mendaftarkan provider yang:
  - memverifikasi ada data hidrasi di TransferState (kalau tidak, hidrasi
    dimatikan dan di dev mode dicetak peringatan NG0505),
  - `verifySsrContentsIntegrity(doc)` memeriksa penanda konten SSR,
  - `enableHydrationRuntimeSupport()` MENUKAR implementasi beberapa fungsi
    runtime (pola "enable...Impl" yang dipakai di seluruh core agar kode
    hidrasi bisa di-tree-shake bila tidak dipakai),
  - menyalakan `PRESERVE_HOST_CONTENT` di browser supaya isi host tidak dihapus.

Saat instruksi pembuatan node berjalan (subsistem 04), setiap node memanggil
`canHydrateNode` -> `locateNextRNode`/`tryLocateRNodeByPath` -> bila ketemu,
`markRNodeAsClaimedByHydration` dan node DOM dipakai ulang. Bila tidak cocok,
terjadi hydration mismatch: dev mode melempar error dengan diff DOM
(`error_handling.ts`), produksi jatuh ke render ulang bagian tersebut.

Setelah aplikasi stabil, `cleanupDehydratedViews` membuang node/view sisa server
yang tidak diklaim siapa pun (`removeDehydratedViews`, `cleanupLContainer`,
`cleanupLView`).

EVENT REPLAY
------------
Masalah klasik SSR: pengguna mengklik sebelum JS selesai dimuat. Solusinya
memakai `primitives/event-dispatch` (port dari jsaction Google):
  - server menambahkan atribut `jsaction="click:;keydown:"` pada elemen yang
    punya listener, dan menyisipkan skrip kecil (`earlyeventcontract.ts`) yang
    memasang listener global di `body` serta MENYIMPAN event ke antrean,
  - setelah runtime siap, `event_replay.ts` memutar ulang event tersimpan ke
    listener Angular yang sebenarnya.

HIDRASI INKREMENTAL (@defer dengan hydrate triggers)
----------------------------------------------------
`withIncrementalHydration()` memungkinkan blok @defer tetap dehidrasi sampai
trigger-nya terpenuhi (`on viewport`, `on interaction`, `on timer`, `when`).
Server menyerialisasi info blok defer + trigger-nya; klien memasang listener
jsaction pada node akar blok (`annotateDeferBlockRootNodesWithJsAction`), lalu
`incremental_runtime.ts` memuat dependensi dan menghidrasi blok saat dipicu -
termasuk menghidrasi seluruh rantai blok induk lebih dulu
(`getParentBlockHydrationQueue`).

I18N
----
Blok i18n memerlukan penanganan khusus karena struktur DOM-nya dibentuk oleh
opcode, bukan instruksi biasa; `withI18nSupport()` menyalakan jalur ini
(`hydration/i18n.ts`).
