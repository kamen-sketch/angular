STRUKTUR DATA INTI: TView / LView / TNode
-----------------------------------------
Angular memisahkan data STATIS (dibagi seluruh instance) dari data INSTANCE:

  TView  - "cetak biru" satu template. Satu TView per komponen/template,
           dibuat sekali. Berisi: template fn, blueprint, data (TNode +
           definisi directive), daftar hook, queries, registry directive/pipe,
           hostBindingOpCodes, flag firstCreatePass/firstUpdatePass.
  LView  - satu instance view. ARRAY (bukan objek) dengan header berukuran
           HEADER_OFFSET=27 slot, lalu slot untuk node, lalu slot binding.
  TNode  - metadata statis satu node template (tipe, attrs, indeks directive,
           providerIndexes, injectorIndex, parent/child/next).

Mengapa LView adalah array, bukan objek: akses berindeks lebih cepat, ukuran
kode lebih kecil (konstanta HOST=0, TVIEW=1, FLAGS=2, ... di-inline oleh
minifier), dan memudahkan alokasi lewat `blueprint.slice()`.

Header LView (indeks 0..26) berisi antara lain:
  HOST, TVIEW, FLAGS, PARENT, NEXT, T_HOST, HYDRATION, CLEANUP, CONTEXT,
  INJECTOR, ENVIRONMENT, RENDERER, CHILD_HEAD, CHILD_TAIL, DECLARATION_VIEW,
  DECLARATION_COMPONENT_VIEW, DECLARATION_LCONTAINER, PREORDER_HOOK_FLAGS,
  QUERIES, ID, EMBEDDED_VIEW_INJECTOR, ON_DESTROY_HOOKS, EFFECTS_TO_SCHEDULE,
  EFFECTS, REACTIVE_TEMPLATE_CONSUMER, AFTER_RENDER_SEQUENCES_TO_ADD, ANIMATIONS

Perbedaan tiga "parent" yang sering membingungkan:
  PARENT                     - induk logis (LView atau LContainer)
  DECLARATION_VIEW           - view tempat template DITULIS (untuk DI & scope)
  DECLARATION_COMPONENT_VIEW - view komponen terdekat (untuk @Host, host binding)
Untuk embedded view yang disisipkan di tempat lain (transplanted view), ketiganya
bisa menunjuk ke tempat berbeda - inilah sumber kerumitan CD transplanted view.

`createTView` menutup objek dengan `Object.seal` di dev mode agar bentuknya
tetap monomorfik (penting untuk optimasi JIT engine JavaScript).

DUA FASE: CREATION vs UPDATE
----------------------------
Template hasil kompilasi berbentuk:

    function Tmpl(rf, ctx) {
      if (rf & 1) { /* creation: elementStart, text, template, ... */ }
      if (rf & 2) { /* update: advance, property, textInterpolate, ... */ }
    }

  - `renderView` menjalankan fase creation (RenderFlags.Create) + view query
    statis + render komponen anak.
  - `refreshView` (subsistem 03) menjalankan fase update.
  - `tView.firstCreatePass` menandai eksekusi pertama sebuah TEMPLATE (bukan
    instance): di situlah TNode dibuat, directive dicocokkan, hook didaftarkan.
    Instance berikutnya memakai ulang seluruh hasil kerja itu.
  - Jika terjadi error saat firstCreatePass, TView ditandai `incompleteFirstPass`
    agar runtime bisa mencoba memulihkan diri.

MODEL BINDING (kenapa `advance` ada)
------------------------------------
Nilai binding disimpan di slot LView setelah `bindingStartIndex`, diakses
BERURUTAN lewat penunjuk global `bindingIndex`. Instruksi update tidak menyebut
indeks slot - urutannya implisit dari urutan pemanggilan. Karena itu compiler
menyisipkan `ɵɵadvance(n)` untuk memindahkan "elemen terpilih" (selected index),
dan `ɵɵadvance` sekaligus menjadi titik eksekusi pre-order hooks yang tertunda.

`bindingUpdated` adalah primitif intinya: bandingkan dengan `Object.is`, simpan
bila berubah, dan (di dev mode + checkNoChanges) lempar
ExpressionChangedAfterItHasBeenCheckedError dengan detail lokasi. Sentinel
`NO_CHANGE` menandai slot yang belum pernah diisi. Varian `bindingUpdated2/3/4`
menghindari overhead pemanggilan berulang untuk interpolasi multi-ekspresi.

SIKLUS PEMBUATAN ELEMEN
-----------------------
`ɵɵelementStart` (dan saudara-saudaranya) mengikuti pola seragam:
  1. firstCreatePass -> `directiveHostFirstCreatePass` membuat TNode, mencocokkan
     directive (`findDirectiveDefMatches`), mengalokasi slot host binding.
  2. Selain itu ambil TNode yang sudah ada dari `tView.data`.
  3. Buat/klaim DOM node - klaim (hydration) bila ada data dehidrasi.
  4. `createDirectivesInstances` -> instansiasi directive + host bindings.
  5. `saveResolvedLocalsInData` mengisi nilai local ref (#ref).

Semua jalur pembuatan node memeriksa hidrasi lebih dulu (`canHydrateNode`,
`locateNextRNode`, `markRNodeAsClaimedByHydration`), sehingga instruksi yang
sama dipakai untuk render baru maupun hidrasi.

CONTROL FLOW BAWAAN (@if / @for / @switch)
------------------------------------------
@if dan @switch dikompilasi menjadi `ɵɵconditional`: sebuah LContainer dengan
banyak template cabang; instruksi hanya memilih indeks cabang, membuang view
lama dan membuat view baru saat indeks berubah.

@for dikompilasi menjadi `ɵɵrepeaterCreate` + `ɵɵrepeater`:
  - `RepeaterMetadata` menyimpan trackByFn dan LiveCollection.
  - `LiveCollectionLContainerImpl` adalah adaptor LContainer ke algoritma
    rekonsiliasi generik (`reconcile` di list_reconciliation.ts) yang memakai
    kunci track-by untuk memutuskan create/move/update/destroy.
  - `ɵɵrepeaterTrackByIndex` / `ɵɵrepeaterTrackByIdentity` adalah dua fungsi
    track bawaan.
  - Di dev mode, `OperationsCounter` mendeteksi kasus "seluruh koleksi dibuat
    ulang" dengan track by identity dan mencetak peringatan - hanya jika view
    dianggap mahal untuk dibuat ulang (`isViewExpensiveToRecreate`).
  - Seluruh `ɵɵrepeater` berjalan dengan `setActiveConsumer(null)`: pembacaan
    koleksi tidak boleh terlacak sebagai dependensi template.

PENGELOLAAN NODE & VIEW TREE
----------------------------
`addToEndOfViewTree` merangkai LView/LContainer anak sebagai linked list
(CHILD_HEAD/CHILD_TAIL/NEXT) - dipakai untuk menelusuri seluruh keturunan saat
destroy dan saat CD. Komentar TODO di kode mengakui urutannya bisa salah bila
LContainer diambil dari RNode secara tidak berurutan.

`allocExpando` memperbesar blueprint + LView + TView.data secara sinkron ketika
node dibuat dinamis (mis. i18nApply).
